## 1. 问题与背景

承接上一篇《项目起点》：选矩阵乘法练手，是因为它是AI Infra里GEMM优化的原点练习。光看教材里的理论分析没体感，这篇只干一件事——拿真实计时数据回答两个问题：①只换循环顺序能差多少？②分块真能再加速吗？

所有对照实验都在同一台机器上跑完：`Windows`、`Intel Core Ultra 7 255HX`、`Visual Studio 2026 18.11.1`（IDE版本）、`Release/x64`（`Day 4`至`Day 7`同机同硬件，当时未单独记录`MSVC toolset`独立版本号，这里如实留白）。计时口径统一卡死：只包`C清零+乘法`，矩阵初始化和结果校验全放在计时外。每个配置测5次取中位数，`Day 5`测循环顺序时还做了样本顺序奇偶交替（先`ijk`后`ikj`/先`ikj`后`ijk`），防运行顺序带来偏差。

---

## 2. 核心原理：内存到底咋走的

C++二维数组按行连续存放，`B[k][j]`和`B[k][j+1]`在内存里紧挨着，而`B[k][j]`和`B[k+1][j]`中间隔着整整一行的`n`个元素。循环顺序一换，访存路线完全变样：

* **`ijk`顺序**：最内层循环扫`k`。`A[i][k]`顺着行往前走，`C[i][j]`固定不动，但`B[k][j]`每算一步就得跨行跳`n`个元素，地址跳跃大、不连续。
* **`ikj`顺序**：最内层循环扫`j`。`A[i][k]`在中间层提前固定住，`B[k][j]`和`C[i][j]`同时顺着行逐元素往后走，两路读写全贴着连续内存跑。

再看分块。分块只改变计算的组织顺序，不改变矩阵乘法的数学定义。拿2×2分块举例，结果矩阵左上角子块满足：

$$C_{00} = A_{00} \cdot B_{00} + A_{01} \cdot B_{10}$$

把大矩阵切成小块算，预期收益是让小块数据留在近处反复复用；但代价同样直接——原本3层循环变成6层循环，外加边界切分判断，循环控制开销全加上去了。

## 3. 关键实现与正确性边界

### 循环顺序核心代码（`src/day05-ijk-ikj-benchmark.cpp`）

```cpp
for (int i = 0; i < n; ++i) {
    for (int k = 0; k < n; ++k) {
        const int aik = A[i][k];
        for (int j = 0; j < n; ++j) {
            C[i][j] += aik * B[k][j];
        }
    }
}
```

这几行把`A[i][k]`提前拎到`k`层循环里固定成标量，最内层`j`只做`C[i][j]`和`B[k][j]`的同向行遍历。写`ikj`有个极容易踩的坑：`C`必须在三层循环开始前一次性清零，要是误写在`k`循环里面、每进一次`k`就清零一次，前面算出来的部分和全被抹掉。

### 分块边界控制

```cpp
int i_end = std::min(ii + block_size, n);
int k_end = std::min(kk + block_size, n);
int j_end = std::min(jj + block_size, n);
```

拿`n=70`、块大小`32`测试时，前两块各占32行，最后一块只剩6行，必须靠`std::min(start + block_size, n)`收尾卡死上界。这里要分清「逻辑越界≠数组越界」：如果底层开的是固定大容量静态数组，下标超出`n`可能不会触发段错误崩溃，但已经读进了脏数据、算错了结果——程序不崩不等于访问安全。

### 三重校验

每组实验都过`C[0][0]预期值+校验和+逐元素比对`三道检查。本篇涉及的105条正式记录（`Day 5`的30条+`Day 7`的75条）全部PASS，逐元素比对全部YES。完整源码、边界测试与原始CSV都在仓库：[github.com/lingquan11/cpp-matmul-performance](https://github.com/lingquan11/cpp-matmul-performance)。

## 4. 实测数据与负结果拆解

### 表1 循环顺序：`ijk`与`ikj`中位数耗时（`Day 5`，5次取中位数，单位ms）

| 阶n | ijk中位数 | ikj中位数 | ijk/ikj |
|---:|---:|---:|---:|
| 64 | 0.140724 | 0.020545 | 6.85× |
| 128 | 1.375541 | 0.162732 | 8.45× |
| 256 | 11.333944 | 1.207955 | 9.38× |

只换两层循环顺序，64阶快了6.85倍、128阶快了8.45倍、256阶快了9.38倍，阶数越大差距拉得越开。但这个比值不是常数，结论只适用于当前实现、当前机器（`Intel Core Ultra 7 255HX`）和64–256阶范围。

### 表2 分块：各配置中位数耗时（`Day 7`，5次取中位数，单位ms）

| 阶n | ijk | ikj | blocked_16 | blocked_32 | blocked_64 |
|---:|---:|---:|---:|---:|---:|
| 64 | 0.142012 | 0.021578 | 0.030522 | 0.024964 | 0.021118 |
| 128 | 1.162850 | 0.150144 | 0.231649 | 0.194287 | 0.166712 |
| 256 | 10.463860 | 1.154853 | 1.843587 | 1.573395 | 1.317015 |

### 表3 分块相对`ikj`的耗时变化（正数代表更慢）

| 阶n | blocked_16 | blocked_32 | blocked_64 |
|---:|---:|---:|---:|
| 64 | +41.4% | +15.7% | -2.1% |
| 128 | +54.3% | +29.4% | +11.0% |
| 256 | +59.6% | +36.2% | +14.0% |

核心结论很直接：**在当前实现与当前机器上，分块没有跑赢朴素`ikj`**。三种块大小里`blocked_64`最快，但也只在64阶比`ikj`快了2.1%（几乎打平）；到了128阶反而慢11.0%，256阶慢14.0%，块切得越碎（`blocked_16`）掉速越狠。

从代码结构看，64–256阶矩阵规模本来不大，`ikj`已经把`B`和`C`拉成连续行访问；强行上分块后，6层循环+`min`边界判断的额外开销吃掉了数据复用收益。但这里必须守住一条解释边界：**总耗时只能证明谁快谁慢，不能直接证明cache miss变多或变少**。要下硬件层面的机制定论，必须采集性能计数器证据，这篇里没测计数器，就不硬编硬件归因。

## 5. 踩坑记录与结论边界

* **负结果摆明面**：分块几乎全线没赢`ikj`（仅64阶`blocked_64`微弱领先2.1%），问题出在当前规模下算法收益没盖过循环控制成本，藏着不写复盘就没参考价值。
* **严格限定适用范围**：本篇所有数字和结论只对当前C++实现、`Intel Core Ultra 7 255HX`平台、64–256阶成立，不能外推成「分块优化没用」——矩阵上到几千阶、换用寄存器分块或叠加SIMD向量化后，局部性收益完全可能反超循环开销。
* **环境记录缺口**：当时只记了IDE版本`Visual Studio 2026 18.11.1`和`Release/x64`，漏记了`MSVC toolset`独立版本号，这篇不倒填版本号，如实留档。
* **下篇留口**：编译选项对照（`/O2`与`/Od`）目前只跑了初步数据，SIMD向量化还没动手，留给《矩阵乘法复盘（下）》继续拆。
