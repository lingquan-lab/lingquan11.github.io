# 长文上站

仓主写长文有两种上站方式，先判断是哪一种。

- **A. 仓主自己推到了 main**（目前最常见）。文章已经上线，你的任务是**上站后复查**，发现问题写进报告，并做好配套更新。
- **B. 仓主把草稿交给你**（文件、粘贴的文本或某个路径）。你负责把它**原样**放进仓库，补好文件头，按 PR 流程交付。

两种情况的共同底线：正文是仓主的作品，一个字、一个标点、一个链接都不改。

---

## A. 仓主已推送：上站后复查

1. **同步代码**：`git fetch origin`，在最新的 `origin/main` 上工作。
2. **确认部署成功**：`gh run list --repo lingquan11/lingquan11.github.io --limit 3`。如果「Build and Deploy」失败，网站会停在上一个版本，不会挂掉。读失败日志（`gh run view <id> --log-failed`），能修的配置问题按 PR 流程修；文章本身的语法问题（例如 front matter 格式错误）告诉仓主怎么改，不要替他改正文。
3. **检查文件头**，对照 README：
   - 文件名 `YYYY-MM-DD-英文短标题.md`，日期和 front matter 里的 `date` 一致，带 `+0800`
   - `categories` 只能是「项目实录」或「深研自述」
   - `tags` 全部在 README 标签词表里；有词表外的，在报告里列出来，请仓主选择：换成词表内的标签，或者批准新标签
   - 全站最多一篇 `pin: true`。新文章也加了置顶的话，问仓主保留哪一篇
4. **检查写作约定**（只报告，不动手）：
   - 是否按六段模板用 `##` 分段：问题与背景、核心原理、实现或推导、数据与验证、踩坑与边界、参考来源。没有 `##` 的话，文章页不会生成目录
   - 内容红线：代码、公式、数据、原理拆解至少占两样
   - 性能数字是否标了机器、尺寸、测法（仓主自己定的规矩）
5. **本地构建并看渲染**：运行 `scripts/verify.sh`（其中的 `lint_markdown.py` 会查表格前后空行等 kramdown 坑，并核对页面里渲染出的表格数；报 E 级错误按下面「排版检查」处理），然后在浏览器里打开这篇文章，按 `pr-and-checks.md` 的手机宽度脚本检查，重点看：
   - 目录是否出现、条目数和 `##`/`###` 数量是否对得上
   - 代码块是否有语法高亮（代码块要标语言名）
   - 公式是否渲染（`mjx-container` 元素）
   - 表格在 375px 宽度下是否在自己的框里横向滚动，整页不能溢出
6. **核对线上**：抓文章网址的 HTML，确认标题、标签、评论区脚本都在，**并核对渲染结果**：页面里 `<table` 的个数等于源文件的表格数，正文段落里没有 `|—|` 这类塌掉的表格文本。只查"文字在不在"会漏掉渲染错误（2026-11-24 就这样漏过一次）。如果看起来是旧版本，先加查询参数（`?nocache=时间戳`）再取一次。GitHub Pages 的 CDN 会把 HTML 缓存最多 10 分钟，别据此下错误结论。**不要执行页面脚本**，否则会给统计记一次访问。
7. **配套更新**（这部分是维护者的活，可以直接做，走 PR）：
   - 仓主为这篇发了封面图，或者文章里有适合画图的数据表，按 `images-and-charts.md` 处理（封面要改 front matter，图表要仓主自己插进正文）
   - 文章属于某个项目时，在 `_data/projects.yml` 对应项目的 `links` 里加上这篇文章，并考虑在 `_data/milestones.yml` 加一个时间线节点
   - 文章里出现了项目页还没有的新进展或新数字，按 `add-project.md` 同步到项目页，数字照抄原文
8. **汇报**：按 SKILL.md 的提醒格式告诉仓主结果。全部正常就一句话："《标题》已上线，渲染和手机排版都正常，项目页已补链接（PR #N）。"

## B. 仓主交来草稿：原样上站

1. **确认信息**。下面这些仓主没给的，先问，不要猜：
   - 标题（正文第一行如果是 `# 标题`，问仓主是否用它作标题。Chirpy 会单独显示标题，正文里再留一个 `#` 会重复，但删不删由仓主定）
   - 发布日期和时间
   - 分类（项目实录 / 深研自述）
   - 标签（从词表里提议 2～3 个，请仓主确认）
   - 英文短标题（用于文件名，提议一个，请仓主确认）
   - 是否置顶
2. **放文件**：`_posts/YYYY-MM-DD-英文短标题.md`。文件头按 README 模板写，字段顺序 `layout, title, date, categories, tags[, pin]`。正文从草稿**逐字节**拷贝。
3. **先跑排版检查**：`python3 .claude/skills/lingquan-blog/scripts/lint_markdown.py _posts/<文件>.md`。有 E 级错误，按下面「排版检查」请仓主确认后再修，不要直接上站。
4. **证明正文没被改动**：对草稿原文和文件中 front matter 之后的部分分别计算 SHA-256，两者必须一致。把哈希写进 PR 描述。换行符保持草稿原样（仓库现有文章都是 LF）。
5. **图片**：草稿引用了本地图片的话，图片放进 `assets/img/posts/<文件名去掉 .md>/`，宽度超过 1600px 的先缩小，尽量压缩。把正文里的图片路径改成站内路径**属于改动正文**，必须先列出要改的每一处，等仓主确认后再改，并在 PR 里逐处说明。
6. **系列文章**：比如《复盘（上）》之后来了《复盘（下）》，可以建议仓主在两篇开头或结尾加互相链接。这同样是改正文，只提建议，由仓主决定、仓主来写或明确授权你写。
7. 然后执行 A 的第 3～7 步（在本地分支上检查），按 `pr-and-checks.md` 交 PR。PR 标题用「新文章：《标题》」。

## 排版检查：kramdown 和编辑器预览不一样

仓主和 muse 写稿用的编辑器、GitHub 预览、掘金都是 GFM；本站用 kramdown。同一份 Markdown，在编辑器里好好的，上站可能塌掉。2026-11-24《1×4脉动阵列乘加单元》的 4 张表就是这样：`#### 表1` 标题下一行直接是表格，站上整张表变成一段竖线文字，`|---|` 还被转成了破折号 `|—|`。

`lint_markdown.py` 查的规则（已用站点同版本 kramdown 实测过）：

| 代号 | 写法 | 站上的结果 | 改法 |
|---|---|---|---|
| E1 | 表格上一行是标题或正文 | 整张表塌成一段文字 | 表格前加一个空行 |
| E2 | 表格下一行紧跟正文 | 整张表塌成一段文字 | 表格后加一个空行 |
| E3 | 第二行不是 `\|---\|---\|`（或里面是破折号） | 不是表格 | 第二行写成半角减号的分隔行 |
| E4 | 用全角竖线 `｜` | 不是表格 | 换成半角 `\|` |
| W1 | 单元格里有 `\|` | 多出一列 | 写成 `\\|` |
| W2 | 独占一行的 `$$` 紧跟正文 | 公式块变成行内公式 | `$$` 前加空行 |

列表、引用、代码块紧跟正文时 kramdown 能正常识别，不用改。

**怎么修**：补空行、改分隔行也是改正文，按硬规则 1 处理：把 lint 的输出（行号和问题）发给仓主，说明"只补空行/只改分隔行，文字一字不改"，得到同意后再改。改完证明只动了排版：

```bash
# 去掉所有空行后比较，应当完全一致（只补空行的情况）
diff <(git show origin/main:_posts/<文件>.md | grep -v '^\s*$') <(grep -v '^\s*$' _posts/<文件>.md) && echo 只改了空行
```

PR 或日志里写明改了哪几行、仓主何时同意。**更好的做法**是提醒仓主写稿时就给表格、公式块前后留空行；交稿前先跑一次 lint。

## 常见坑

- **YAML 里的特殊字符**：标题里有英文冒号、`#`、引号时，整个标题要用双引号包起来。仓库现有文章都用了双引号，照做即可。
- **`C++` 这类标签**：Jekyll 生成网址时会去掉 `+`，C++ 的标签页网址是 `/tags/c/`。以后如果有人想加「C」标签，两者会撞在同一个网址上，要提醒仓主换个名字。
- **未来日期**：`date` 晚于构建时间的文章，Jekyll 默认不会生成。仓主想定时发布时要说明这一点：文章会在日期之后的下一次构建才出现，而构建只在有推送时触发。
- **文章网址**：格式是 `/:year/:month/:day/:title/`，发布后不要改文件名或日期，否则旧链接和评论区（giscus 按网址路径对应讨论）都会断。
