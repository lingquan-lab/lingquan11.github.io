# 新项目上站、项目进展同步

导师看项目页，就是在看"这个人做成过什么"。所以这一页要做到三点：每个数字都有出处、写清没做到的部分、状态是最新的。

项目页的内容在 `_data/projects.yml`（项目卡片）和 `_data/milestones.yml`（顶部里程碑时间线），`_tabs/projects.md` 只负责排版。由维护者维护，改动走 PR。关于页 `_tabs/about.md` 是仓主本人的语气，不在这里改（见文末）。

## 1. 收集事实

仓主通常会说"我开了个新仓库 xxx"，或者体检发现了一个还没上站的公开仓库。先把能读到的都读一遍：

```bash
R=lingquan11/<仓库名>
gh api repos/$R --jq '{description, created_at, pushed_at, topics, license: .license.spdx_id, fork, archived, private}'
gh api repos/$R/readme --jq .content | base64 -d          # README 原文
gh api repos/$R/commits --jq '.[0:15][] | .commit.author.date[0:10] + " " + (.commit.message|split("\n")[0])'
gh api repos/$R/releases --jq '.[] | .tag_name + " " + .published_at[0:10]'
```

- **私有仓库**用 `lingquan-lab` 读不到，直接问仓主要上站哪些信息，不要猜。
- **muse 私下知道的进展**（仓主聊天时提到、还没写进仓库的）：先问仓主"这个可以公开吗"，同意后才能写上项目页，并在 PR 的数字出处表里注明"仓主同意公开（日期）"。不要写成"据 muse 了解"之类暴露私下渠道的说法。
- **fork 来的仓库、博客仓库本身、已归档的仓库**默认不上站，除非仓主要求。

从材料里提取这些信息，每条都记下出处（文件、行号或提交号）：

| 要什么 | 例子 | 找不到怎么办 |
|---|---|---|
| 一句话说清做什么 | "1×4 脉动阵列乘加单元，从规格到门级网表" | 问仓主 |
| 状态 | 进行中 / 已完成 / 第一版已开源 / 暂停 | 看最近提交和 README，拿不准就问 |
| 时间 | 2026年10月起、2026年11月14日完成 | 用首次提交日期并注明"起"，或者问 |
| 技术栈 | Verilog / Python / Yosys | 从 README 和文件类型看 |
| 关键数字，连同测法 | "128阶快8.45倍（各尺寸跑5次）" | **没有就不写**，绝不估算 |
| 没做的部分 | "未做：工艺库映射、时序分析" | 仓主的风格是把边界写清楚，README 里有就照搬 |
| 相关文章 | 站内哪几篇写到了它 | 在 `_posts/` 里搜仓库名 |

## 2. 写条目

在 `_data/projects.yml` 里照现有条目的格式加一项，不要另起一套：

```yaml
- title: 项目名
  status: 进行中            # 卡片左上角的徽章文字
  status_kind: active       # active 进行中（绿点）/ done 已完成（对勾）/ open 已开源 / team 团队角色
  meta: 2026年10月起 · 计划12月10日前收尾
  stack: [C++]              # 技术栈小标签，只写材料里出现过的
  metric: { value: "8.45×", label: 只换循环顺序，128 阶加速 }   # 卡片上突出的一个数字，没有就删掉这一行
  bullets:
    - 关键结果一（数字照抄原文，带上测法或条件；支持 **粗体**）
    - 未做：……（如果有）
  links:
    - { text: "GitHub：仓库名", url: "https://github.com/lingquan11/仓库名" }
    - { text: 相关文章标题, url: /年/月/日/文件名/ }   # 以 / 开头的是站内链接
```

有了新的阶段性成果（立项、完成、开源、发了复盘文章），在 `_data/milestones.yml` 按时间顺序加一个节点。计划中的节点写 `planned: true`，日期过了要更新或删掉。

- 站内链接写以 `/` 开头的路径，模板会自动处理；外链写完整网址。htmlproofer 会检查站内链接是否有效。
- 语气跟随仓主：短句、不夸张、负结果照写。不用"显著提升""业界领先"这类词。
- **顺序**：进行中的主项目在最前，已完成的按重要程度往后排。新条目插在哪里，在 PR 里说明理由，由仓主审定。
- **数字出处表**：PR 描述里列一张"数字 → 出处"的表，仓主审阅时可以逐条核对。

## 3. 进展同步

每周体检（`scripts/audit.py`）会比较各项目仓库的最后推送时间和项目页内容（`_data/projects.yml`）的最后修改时间。仓库更新得更晚，说明项目页可能落后了：

1. 读这段时间的提交记录和 README 的变化（`gh api repos/$R/compare/<旧提交>...<新提交>`，或者直接对比 README 新旧版本）。
2. 有新的里程碑或数字，就按第 2 步的规则更新条目，走 PR。
3. 只是日常提交、没有可写的结果，就不用改，在维护日志里记一句"已看过，无需更新"，免得下次重复检查。
4. 条目里写着"计划某月某日前收尾"而日期已过：不要自己改状态，去问仓主——是已经完成、延期了，还是暂停了。

## 4. 提醒仓主的时机

- **项目完成了，但站上还没有对应的文章** → 建议仓主写一篇复盘，题目和六段大纲可以根据仓库内容先拟一个给他参考（只是建议，正文由他写）。
- **一个项目在项目页上"进行中"超过一个月，却没有新提交** → 问一句状态。
- **新仓库已经公开一周以上，还没上站** → 问仓主要不要放上来。有的仓库仓主不想展示，他说不放，就在维护日志里记下来，以后不再问。

## 关于页

`_tabs/about.md` 的「做过的事」「现在在做的」是仓主用第一人称写的。项目有变化时，体检会提醒关于页可能过时。这时把建议改成什么写成文字发给仓主，由他决定是自己改，还是授权你按原样改。不要直接提交关于页的修改。
