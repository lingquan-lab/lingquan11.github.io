# 体检与提醒仓主

仓主要的是"网站上缺什么、我该做什么"。体检的目的是把这两件事尽早、具体地告诉他，而不是生成一份冗长的健康报告。

## 怎么运行

在仓库根目录运行：

```bash
python3 .claude/skills/lingquan-blog/scripts/audit.py            # 完整体检（需要 gh 已登录 lingquan-lab）
python3 .claude/skills/lingquan-blog/scripts/audit.py --offline  # 只查本地仓库，不访问网络
```

脚本只读：不改文件、不推送，也**不碰 GoatCounter**。它输出一份 Markdown 报告，分成「需要仓主处理」「维护者可直接处理」「正常」「没能检查」四节。你的工作是**解读**这份报告，再按下面的模板写给仓主，不要把原始输出直接贴给他。

先 `git fetch origin && git checkout --detach origin/main`（或者在最新 main 上的任何分支）再运行，否则查的是旧内容。

## 检查什么、什么时候提醒

| 检查 | 触发提醒的条件 | 归谁处理 | 为什么重要 |
|---|---|---|---|
| 更新节奏 | 距上一篇文章超过 7 天提醒，超过 14 天强调 | 仓主 | README 写着"一周一篇左右，不断更优先于写得长" |
| 栏目覆盖 | 「项目实录」或「深研自述」没有文章 | 仓主 | 导师点进空栏目，观感很差 |
| 标签 | 文章没打标签，或用了词表外的标签 | 仓主决定，维护者执行 | 标签是读者按主题浏览的入口 |
| 小标题 | 2026-11-22 之后发的文章没有 `##` | 仓主（下一篇注意） | 没有小标题就没有目录，长文很难读 |
| 内容红线 | 近 30 天的文章里，代码块、公式、表格一样都没有 | 仓主（人工判断） | README 红线：代码、公式、数据、原理至少两样。脚本只能粗筛，可能误报 |
| 置顶 | 置顶不止一篇，或者一篇都没有 | 仓主 | 首页第一印象 |
| 项目页过时 | 某个项目仓库的推送时间晚于项目页的最后修改时间 | 维护者 | 见 `add-project.md` 第 3 节 |
| 计划日期已过 | 项目页写着"计划某月某日前…"，日期已过但状态仍是"进行中" | 仓主说明，维护者更新 | 过期的计划会让人觉得项目烂尾了 |
| 新仓库未上站 | 仓主有公开、非 fork 的仓库没出现在项目页 | 仓主决定要不要放 | 做了的东西应该被看到 |
| 关于页 | 超过 60 天没更新 | 仓主 | 「现在在做的」很容易过时 |
| 评论 | 文章评论区里最新一条不是仓主的回复 | 仓主 | 同行的提问没人回，比没有评论区还糟 |
| 待审 PR | `lingquan-lab` 提的 PR 开着超过 3 天 | 仓主 | 改动在排队，网站没有更新 |
| 部署 | main 上最近一次「Build and Deploy」失败 | 维护者 | 网站会停在旧版本 |
| Pages 设置 | 部署方式不是 GitHub Actions（`build_type` 不是 `workflow`） | 仓主 | 两套部署会抢着发布，可能把源文件直接发上线 |
| 主题版本 | rubygems 上的 Chirpy 比本地锁定的版本新 | 维护者 | `Gemfile` 写的是 `~> 7.6`，线上构建会自动用最新的 7.x，被覆盖的主题文件可能对不上 |
| 静态资源包 | `assets/lib` 子模块落后于上游 | 维护者 | 主题升级后资源包也要跟上 |

## 仓主说过"不用了"的事：写进忽略清单

仓主明确说某件事不用再提醒（例如"这个仓库我不想放上站"），就在 `.claude/skills/lingquan-blog/audit-ignore.txt` 里加一行，随下一个 PR 提交，并在维护日志里记下日期。脚本会跳过这些项目，不再提醒。这个文件是公开的，备注只写"仓主决定"这类中性说法，不写私人原因：

```
# 格式：<类型>:<值>    # 原因（日期）
repo:some-private-experiment      # 仓主不想上站（2026-12-01）
redline:2026-10-29-ai-chip-explorer.md  # 工具发布帖，仓主认可（2026-12-01）
```

支持的类型：`repo`（仓库名）、`redline`、`headings`、`tags`（文章文件名）、`category`（栏目名）、`check`（整项检查的名字，见脚本输出里方括号中的编号）。

## 结合仓主近况（muse 专属）

脚本只看得到仓库和 GitHub，看不到仓主的生活。muse 写报告前，用自己掌握的近况把脚本结果过一遍：

- **调整轻重**：脚本说"断更 10 天"，但仓主这周在考试，就写成"考完再写也来得及，到时候可以写……"，或者干脆推到下周报告。
- **补上脚本看不到的事**：仓主说过某个项目刚跑通、某个实验刚有数据，就提醒"这值得写一篇"，或者"要不要更新项目页"（先确认能否公开）。
- **选题建议要贴着他最近做的事**，而且要具体：给出题目和六段大纲的骨架。

报告是私下发给仓主的，可以写这些近况。但报告里的内容不要提交进仓库：日志里只记"发了周报、提醒了哪几类事"，不记私人细节。

## 写给仓主的报告

用中文，简短，按这个模板。没有内容的小节整节删掉，不要写"无"。

```markdown
## 网站周报（YYYY-MM-DD）

### 需要你做的
1. **<一句话说清楚做什么>**：<为什么，一句>。<具体建议，例如可以写的题目、需要你回复的评论链接>
2. ……

### 我已经处理/准备处理的
- <做了什么>（PR #N，等你审阅）

### 可以考虑（不急）
- ……
```

写作要点：

- **一条一个动作**。"更新关于页"太含糊；"关于页『现在在做的』还写着 cpp-matmul 进行中，项目页显示它已完成，要不要改成……"才能让仓主马上动手。
- **给建议，而不只是指出问题**。提醒更新节奏时，可以根据最近的仓库提交，建议一个现成的选题。
- **数字要准**。"距上一篇 9 天"，而不是"有段时间没更新了"。
- **全部正常就一句话**："这周网站没有需要你处理的事。"

## 定时运行

技能本身不会自己触发。要做到"及时提醒"，需要定期运行：

- **muse 长期接管时**：每周固定一天（建议周一）运行完整体检并发报告。仓主每次推送新文章后，再做一次上站复查（`publish-post.md` A 部分）。
- **用 Claude Code 时**：可以创建一个每周执行的定时任务，提示词写"按 lingquan-blog skill 做每周体检，把报告发给我"。这需要仓主同意后再设置。
- **紧急情况立即报**，不等周报：部署失败、Pages 设置被改、评论区有人提了具体的技术问题。
