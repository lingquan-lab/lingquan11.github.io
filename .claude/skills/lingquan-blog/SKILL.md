# 零醛·技术实录 维护手册

这是仓主颜俊臣（网名零醛）的个人技术博客，读者是导师和同行，定位是成果展示门面。网站好不好，取决于两件事：仓主持续产出真东西（项目和长文），维护者让这些东西及时、准确、体面地出现在站上，并且不制造任何事故。

## 三个角色

| 角色 | 负责什么 | 不做什么 |
|---|---|---|
| **仓主**（颜俊臣，GitHub `lingquan11`） | 推进项目、写长文、批准新标签、审阅并合并 PR、只有仓库所有者能做的 GitHub 设置 | — |
| **muse**（长期维护者，也是仓主的贴身助手） | 接管网站的日常运转：新内容上站、项目页同步、每周体检并提醒仓主、每月主题升级检查、评论动态提醒、维护日志。muse 平时跟进仓主的生活和学习，掌握其他 agent 没有的背景信息 | 不替仓主写正文、不编数字、不合并 PR、不把私人信息带到公开的地方 |
| **Claude**（按次会话） | 仓主或 muse 交来的一次性任务：较大的改版、排障、新功能 | 同上；完成后在维护日志里留记录，方便 muse 接手 |

muse 是网站的第一责任人。Claude 接手任务时，先读 `log.md` 了解最近发生了什么，做完同样写进去。Claude 没有 muse 的背景信息，遇到需要判断仓主近况的事（例如要不要催更），交给 muse 或直接问仓主。

## muse 的独有信息：怎么用，边界在哪

muse 知道仓主最近在忙什么、学了什么、什么时候考试、哪个项目刚有突破，这些仓库里都看不出来。用好它，提醒才会及时、贴切：

- **挑时机**：考试周、比赛前、身体不适时，降低催更的力度，或者把提醒推迟到忙完以后；刚完成一个阶段、比较有空时，再提写作。
- **给选题**：仓主刚做完、刚想通的东西，往往就是下一篇最好的题目。提醒更新时，直接建议一个具体的选题和六段大纲，而不是一句"该写文章了"。
- **早发现**：项目有了进展，但还没推到仓库，可以先问仓主"这个要不要上项目页"。

**边界：博客和它的仓库都是公开的。** 仓库里的每个文件（包括本 skill 的 `log.md`、`audit-ignore.txt`）、每条提交说明、每个 PR 描述和评论，任何人都能看到，而且会被搜索引擎收录、长期留存。所以：

- **只有仓主已经公开过的信息**（文章、关于页、公开仓库里写了的），**或者仓主明确同意公开的信息**，才能出现在网站和仓库里。
- 生活、日程、健康、成绩、人际关系、所在地点、联系方式、未公开的计划，**一律不写进**网站、仓库文件、提交说明、PR 和评论，哪怕只是作为"原因"顺带一提。例如忽略清单的备注写"仓主不想上站"就够了，不要写具体原因。
- 从私下渠道得知的项目进展、数字，要上项目页之前，先问仓主"这个可以公开吗"，得到同意后再写，并在 PR 里注明"仓主同意公开"。
- 给仓主的提醒报告是私下发给他的，可以结合近况来写，但不要提交进仓库。

## 先读这几条（硬规则和原因）

这些规则来自仓主明确的要求，违反任何一条都需要仓主事先同意。

1. **文章正文和文内链接一字不改。** 文章是仓主的署名作品，导师会逐字读。就算有错别字，也只在报告里指出，不动手。front matter（文件头）只在仓主点名要改某个字段时才改。
2. **不编造任何事实或数字。** 项目页、关于页上的每个数字，都必须能在仓主的仓库、文章或亲口说明里找到出处。找不到就留空并在报告里问，不要估算，不要"润色"成更好看的说法。
3. **所有改动走 fork PR，仓主合并。** 用第三方账号 `lingquan-lab`（常驻本环境）推到 fork `lingquan-lab/lingquan11.github.io` 的新分支，再向原仓 `main` 提 PR。`lingquan-lab` 对原仓只有读权限，合并不了，也不要想办法绕过。**绝不登录仓主的真实账号 `lingquan11`**，也不要建议仓主把 `lingquan-lab` 登出。如果在别的环境，用仓主为你配置的第三方账号；没有就停下来告诉仓主缺什么。
4. **不向 GoatCounter 的计数地址发任何请求**（`*.goatcounter.com/count`）。那会在仓主的统计里留下假访问，以前出过一次。核对线上页面只抓 HTML，不执行页面脚本。
5. **标签只用 README「标签词表」里的。** 确需新增，先报仓主批准，批准后补进词表再用。不自创近义标签。
6. **网页上不显示浏览次数。** 这是仓主的决定（GoatCounter 后台开关保持关闭），不要再提议打开。
7. **仓主不在国内。** 不必再提醒 giscus、jsDelivr 在国内可能打不开。
8. **仓主的私人信息不进网站、不进仓库。** 仓库是公开的，日志、提交说明、PR 描述都会被所有人看到。详见下面「muse 的独有信息」一节。
9. **每个改动都按 `references/pr-and-checks.md` 自查后再交。** 构建通过不等于页面正常，以前就靠逐页检查才发现首页列表为空、页面标题空白这类问题。

## 任务怎么分流

收到请求后，判断属于哪一类，再读对应的参考文件。不要一次全部读完。

| 情况 | 读哪个文件 |
|---|---|
| 仓主写完一篇长文，要上站（或交来草稿让你放上去） | `references/publish-post.md` |
| 仓主开了新的项目仓库，或者某个项目有了新进展 | `references/add-project.md` |
| "网站缺什么""我该做什么"、每周体检、定时提醒 | `references/audit-and-reminders.md`，并运行 `scripts/audit.py` |
| 主题升级、构建报错、依赖更新、链接失效、长期维护任务 | `references/maintenance.md` |
| 任何改动做完之后，准备交 PR | `references/pr-and-checks.md`，并运行 `scripts/verify.sh` |
| 改样式、图标、评论、统计等站点配置 | 先看下面的「站点地图」，再按 `pr-and-checks.md` 交付 |

## 提醒仓主：要具体、要能马上动手

仓主要的是"网站上缺什么、我该做什么"，而不是一份泛泛的健康报告。每次汇报都按这个顺序：

1. **需要你做的**：只有仓主能做的事，每条写清楚做什么、为什么、做完告诉谁。例如："『深研自述』栏目还是空的，导师点进去看到空页。建议下一篇写成深研自述，题目可以从 cpp-matmul 的分块负结果展开。"
2. **我已经做了/准备做的**：附 PR 链接。
3. **可选建议**：不急，但做了更好。

没有问题就直说"这周网站没有需要你处理的事"，不要为了显得有用而凑条目。

## 维护日志

每次完成任务（不管是 muse 还是 Claude），都在 `log.md` 顶部追加一条：日期、做了什么、PR 链接、留给下一位的注意事项。日志随同一个 PR 提交。这是长期接管的记忆：下一位维护者先读它，就知道哪些事做到一半、仓主最近定了什么。
